# Структура идентификаторов согласована 15.10.2026

Пользователь подтвердил сохранение UUID, неизменяемые canonical_key и единую
таблицу общих/личных упражнений. Реализация разбита на совместимые этапы.

## Идентификаторы и совместимость

1. Существующий exercises.id (UUID) неизменен. Имена никогда не ключи.
2. Для новых упражнений UUID создаётся один раз и фиксируется в наборе данных;
   повторная загрузка использует тот же UUID, не генерирует его заново.
3. canonical_key — уникальный неизменяемый ASCII snake_case, например
   barbell_bench_press или forearm_plank. Изменение русского имени ключ не меняет.
   Личная запись: user_<uuid без дефисов>; это не механизм авторизации.
4. families и справочники имеют постоянные code и UUID; labels можно менять.
5. Подтверждённый дубль не удалять и не перепривязывать историю автоматически:
   retired + canonical_exercise_id через проверенную карту. Старый UUID остаётся
   доступен, поиск показывает каноническую карточку. Аналитика по старым ID сохраняется.
6. Для импорта из JSON legacy_source включает source_key, а legacy_exercise_id —
   устойчивый адрес элемента (workout/exercise ordinal в зафиксированной версии).
   Одного имени недостаточно: разные программы могут подразумевать разные варианты.

## Сущности

Расширяем exercises, не создаём параллельный каталог. name сохраняется как совместимое
поле русского названия; API v2 отдаёт name_ru из него. difficulty smallint 1–3 сохраняет
старый контракт, новый интерфейс отображает начинающий/средний/продвинутый.

Добавляем: canonical_key, family_id, parent_exercise_id, activity_type, mechanics,
body_position, laterality, primary_muscle_group_id, movement_pattern_id,
short_description, setup_instructions, execution_steps, technique_cues,
common_mistakes, safety_notes, measurement_type, load_mode, status, updated_at.
Списки инструкций — массивы текста; никакого слияния их со служебными notes.

Справочники: exercise_families (иерархия), movement_patterns, muscle_groups, muscles,
equipment_types. Расширяемые признаки — таблицы с уникальным code, не свободный текст.
UI muscle_groups сохраняет 10 групп из ТЗ; equipment_types связывает расширенные
типы с прежними группами фильтра. Скамья — дополнительное оборудование, а не замена
основной штанги/гантелей. Нужны также силовая рама и ролик из обязательных карточек.

Связи: exercise_aliases (ru/en, тип), exercise_muscles (primary/secondary/stabilizer),
exercise_equipment (main/additional), exercise_movement_patterns (secondary),
exercise_relations (variant_of/alternative_to/progression_of/regression_of).
Уникальность aliases — внутри упражнения по нормализованному тексту и языку;
общий alias может вести к нескольким значимым вариантам. Самоссылки запрещены.
Основной паттерн не дублировать вторичной связью. Индексы внешних ключей обязательны.

machine_profiles хранит конструкцию, механизм нагрузки, траекторию и настройки,
без бренда как идентификатора упражнения. Связь exercise_machine_profiles — M:N.
equipment_instances содержит owner_user_id, профиль, производителя, модель, название,
место и настройки. exercise_configurations — пользовательские параметры выполнения;
в сессии сохраняется снимок конфигурации, чтобы последующее редактирование не меняло историю.

exercise_media: тип, путь, источник, лицензия; без медиа используется штатная заглушка.
exercise_legacy_mappings: составной ключ source/id, исходное имя, nullable canonical UUID,
решение, статус проверки, обоснование. Неразобранная строка не означает сопоставление.
Для составных строк программы требуется отдельная модель блока/упражнений, не один UUID.

## Личные данные и доступ

Личные упражнения остаются в exercises(owner_id). При необходимости user_exercises —
только security_invoker view, не вторая таблица. Общие карточки редактируются только
доверенным процессом публикации. Все связанные таблицы включают RLS; доступ к связям
проверяет доступность упражнения, не только факт входа. Экземпляры оборудования и
конфигурации доступны исключительно владельцу. UPDATE проверяет и старого, и нового
владельца; нельзя перенести частное упражнение в общий каталог сменой owner_id.
GRANT выдаётся явно. Ключей service_role в клиенте нет и добавляться не должно.

Глобальный UNIQUE(name) заменить только вместе с отказом импортера от выбора LIMIT 1.
Уникальность общей идентичности обеспечивает canonical_key; личные имена не глобальны.
На этапе публикации проверять смысловые дубли отдельно от строковой уникальности.

## Результаты и история

Добавить nullable duration_seconds, distance_meters, assistance_weight, side,
equipment_instance_id, configuration_snapshot, measurement_snapshot, metric_version.
Для новых результатов: weight_reps/bodyweight_reps/assisted_reps/duration/carry/cardio.
Позднее можно расширять справочник. Односторонность — независимый признак результата,
а не замена weight_reps. Помощь хранить отдельно от дополнительного веса.
Вес штанги включает гриф; гантели — одна гантель; машина — указанное сопротивление.

Существующие подходы остаются legacy_v1: значения, завершённость, set_type, тоннаж,
лучший подход и прежний результат не пересчитываются. Новые метрики сравниваются только
в совместимом measurement/load/equipment контексте. При неизвестном тренажёре не
заявлять сопоставимость механической нагрузки. Разминка не участвует в рекордах.

## Последовательность внедрения и приёмка

1. Согласование UUID/ключей/общей таблицы. Сохранение контрольных количеств и снимков.
2. Только добавляющая схема: новые поля nullable, новые справочники и RLS. CLI создаёт
   migration file; проверка на изолированной базе и повторный запуск загрузчика.
3. Наполнение карточек (draft → review → published). Ограничения обязательных полей
   действуют для published; старые карточки сохраняют совместимый legacy-статус.
4. Проверенные mappings, обновлённый импортер, поиск aliases/семейства, фильтры,
   recent 10, mine, просмотр старых UUID. Ввод новых метрик за флагом.
5. Проверка двумя пользователями (чтение/создание/редактирование чужих сущностей),
   целостность связей и неизменность старых подходов/заметок/снимков.
6. Сборка и регрессионные тесты, тест публикационного барьера, повторного импорта,
   неоднозначных alias и составных строк, замены упражнения и восстановления черновика.
7. Контролируемое включение. Откат приложения на старый контракт без удаления новых
   таблиц и без обратного пересчёта истории. Первая добавляющая миграция подготовлена
   и проверена локально; в production НЕ применена. Этот документ не SQL-миграция.
